# zigbee-rs-hub

[English version](README.md)

Самостоятельный Zigbee-хаб на Rust для платы **Espressif Thread Border Router /
Zigbee Gateway** (хост ESP32-S3 + радио ESP32-H2). На H2 работает NCP
[zigbee-rs](https://github.com/faronov/zigbee-rs), на S3 — хаб, который
общается с ним по **ZRHP v1** (протокол хоста zigbee-rs, спецификация:
`docs/book/src/advanced/host-protocol.md` в zigbee-rs) через UART платы.

ZRHP остаётся протоколом для USB/UART (сетевого транспорта нет). Внешний
интерфейс самого хаба — WebSocket JSON API.

## Этапы

| Этап | Содержание | Статус |
|---|---|---|
| **0** | Прошивка S3 `tbr-bridge`: мост USB ↔ UART H2 с автосбросом esptool, чтобы H2 можно было прошивать и опрашивать с компьютера; бэкапы флеша обоих чипов | **готово**: на плате мост 0.2.2; esptool через автосброс, проверенные бэкапы обоих чипов, обмен spinel; перепрошивка S3 через hwlab без кнопок; RTS/CTS на резервных линиях, замерено до 2 Мбод (см. «Статус») |
| **1** | ZRHP-хост на S3 на `zigbee-zrhp` (`std`): сессия, ARQ, кредиты, восстановление; жизненный цикл NCP на H2: определение размера флеша, обновление `FW_*` в неактивный слот H2 с пробной загрузкой, подтверждением и **откатом на стороне H2** (A/B-слоты; S3 не хранит образы NCP); восстановление через ROM-загрузчик H2 — только ручной путь с образом от оператора | **в работе** (ветка `phase1`): ядро хоста `hub-ncp` проверено на симулированном NCP, `hubctl` на macOS, прошивка `tbr-hub` (режим хаба + мост как режим по умолчанию); на железе: сбросы и восстановление, длительный прогон, обновление `FW_*` с откатом и подтверждением, `tbr-hub` на S3 (см. «Статус этапа 1») |
| **2** | Самостоятельный хаб: таблицы на стороне хоста (подкачка, журнал хранилища хоста), WebSocket JSON API, Wi-Fi и Ethernet W5500, PTA-сосуществование включается автоматически при работающем Wi-Fi | **в работе** (ветка `stage2`): движок на ядре хоста, реестр устройств в `hubdata`, WebSocket JSON API на компьютере (`hubctl serve`) и на S3 через Wi-Fi, проверка каталога, разметки 8 МБ (продукт) / 4 МБ (разработка); сборка приложения для S3 — 2,1 МиБ, см. «Этап 2» |

## Релизы и веб-прошивальщик

Прошивки для платы берутся из GitHub-релизов с тегами (`hub-v*` в этом
репозитории для S3, `ncp-v*` в zigbee-rs для H2) и ставятся из браузера:
**<https://faronov.github.io/zigbee-rs/flasher/>** (Chrome или Edge на
компьютере, Web Serial, [ESP Web Tools](https://esphome.github.io/esp-web-tools/);
подробности в книге zigbee-rs, глава «Web Flasher»).

| Пункт в прошивальщике | Порт | Образ |
|---|---|---|
| Thread Border Router board, S3 (4 MB / 8 MB, определяется) | S3, USB2 | `tbr-hub`: рабочая разметка (A/B OTA) на 8 MB, dev-разметка (без OTA) на 4 MB |
| Thread Border Router board, H2 | H2, USB1 | ZRHP NCP, UART 921 600 с RTS/CTS |

- **Размер флеша:** для S3 прошивальщик сначала читает ID флеша и таблицу
  разделов (*Connect and read the flash size*) и выбирает самый большой
  подходящий образ; образ для 8 MB на чип с 4 MB не предлагается (он бы не
  загрузился). Если на чипе другая таблица разделов (например, 4 MB dev →
  8 MB), стирание обязательно: сначала сделайте бэкап сети (веб-интерфейс или
  `network/backup`).
- **Обновление (по умолчанию)** пишет загрузчик, таблицу разделов, пустой
  `otadata` (8 MB) и приложение; `nvs` (Wi-Fi, режим загрузки, токен API) и
  `hubdata` (реестр устройств, хранилище ZRHP-хоста) остаются. В диалоге
  ESP Web Tools галочку *Erase device* не ставить.
- **Стирание** (галочка на странице) — для первой установки поверх прошивки
  Espressif или tbr-bridge со стандартной разметкой, либо чтобы сбросить хаб.
  H2 и его сеть не затрагиваются.
- Пока работает tbr-hub или tbr-bridge, на USB2 видны два порта моста, а не
  USB-Serial-JTAG самого S3: сначала переключите его кнопкой на странице
  (касание 1200 бод на втором, консольном порту) или командой консоли
  `s3 usj`. После установки S3 стартует в режиме моста; `mode hub` и
  `wifi set <ssid> <password>` в консоли делают из него хаб. Консоль в
  браузере <https://faronov.github.io/zigbee-rs/flasher/console/> делает это
  через форму (*Set up Wi-Fi*: Wi-Fi, режим хаба, адрес и токен API в виде
  ссылки на веб-интерфейс) и служит терминалом для второго (консольного)
  порта.
- Образы для 8 MB ещё не запускались на плате с 8 MB (пока только образец
  на 4 MB).

**Как выпустить релиз:** выставить версию в `firmware/hub/Cargo.toml` и
`CONFIG_APP_PROJECT_VER` (`firmware/hub/sdkconfig.defaults`), обновить
`Cargo.lock` (`cargo update -p tbr-hub`), закоммитить, затем
`git tag hub-vX.Y.Z && git push origin hub-vX.Y.Z`. `hub-release.yml`
проверяет версии (и ту, что в собранном приложении), собирает
закреплёнными версиями инструментов и прикладывает для каждой разметки
полный образ флеша (`…-merged.bin`, смещение 0, дополнен до размера флеша),
загрузчик, таблицу разделов, пустой `otadata` (8 MB), приложение, а также
приложение `tbr-bridge`, `release-manifest.json` и `SHA256SUMS`; в описании
релиза — команды esptool. Обе разметки содержат MQTT; образы 8 МБ также
включают расширенную консоль и хранилище образов Zigbee OTA (`features` у
каждой платы в манифесте; `tools/build-hub-firmware.sh`). Суффикс (`hub-v0.2.0-rc.1`) делает пре-релиз.
Прошивальщик подхватывает релиз в течение шести часов, или сразу, если в
этом репозитории есть секрет `FLASHER_DISPATCH_TOKEN` (fine-grained token,
*Contents: read and write* на faronov/zigbee-rs).

### Варианты образов и память (после релиза 0.2.0)

Требования к платам и backend'ам, матрица функций и готовности:
[Firmware profiles and coordinator backends](docs/coordinator-profiles.md).

Образ 4 МБ сохраняет таблицу разделов, `nvs`, `hubdata` и выбор режима
загрузки. Обычные сборки — фича `mqtt` (4 МБ) и `mqtt,advanced,ota-store`
(8 МБ): в обеих остаются устройства ZCL, Tuya и Green Power,
группы/сцены/привязки, автоматизации, каталог, WebSocket/HA и ESP-IDF
esp-mqtt. Ручная ZCL/Tuya-консоль и просмотр живых кадров вынесены в фичу
`advanced`; без неё соответствующий API отвечает `unsupported`. Наличие
консоли сообщает `hub/info.advanced`. OTA-сервер Zigbee для устройств
(`ota`; `ota-store` добавляет хранилище образов во втором слоте
приложения разметки 8 МБ и включает `ota`) есть только в образах 8 МБ:
образы 4 МБ собираются без него (нет `ota` в `hub/info`, `ota/*` отвечает
`unsupported`, нет вкладки Updates).

```sh
RUSTUP_TOOLCHAIN=esp tools/build-hub-firmware.sh --layout 4mb --locked
# Только Octal или расширенная сборка для 4 МБ:
RUSTUP_TOOLCHAIN=esp tools/build-hub-firmware.sh --layout 4mb --psram octal --locked
RUSTUP_TOOLCHAIN=esp tools/build-hub-firmware.sh --layout 4mb --locked -- --features advanced
```

Каждый образ помечает в бинарнике свои фичи и режим PSRAM;
`tools/release-images.py` отклоняет образ, метка которого не совпадает с
описанием платы (например, сборку 8 МБ, оставшуюся в каталоге 4 МБ).

Quad/Octal — интерфейс установленной PSRAM, а не её объём; для 2, 4, 8 и
16 МБ лимиты одинаковы: семь HTTP-сокетов, 128 КиБ в очереди на
WebSocket-клиента (384 КиБ всего). Снимок подписки уходит фрагментами
одного WebSocket-сообщения, каждый создаётся после отправки предыдущих, так
что большой непрерывный буфер не нужен. `hub/system` сообщает
`memory_mode`, `build` образа (фичи, режим PSRAM) и эти `limits`.

Каждый образ определяет PSRAM при старте. Без неё (образ собран под другой
интерфейс или у модуля её нет) приложение **не запускается**: на
лабораторной плате N4R8 Quad-образ оставлял ~35 КБ внутренней кучи и падал,
как только подключались клиенты, — данные приложения и буферы Wi-Fi/lwIP
иначе лежат в PSRAM. Ядро хаба сохраняет сеть Zigbee (сессия NCP, хранилище
хоста); веб-страница, `/api` (HTTP 503, `psram_missing`) и `info` в консоли
говорят, какой образ прошить. Режим приложения только на внутренней RAM
требует примерно на 100 КБ меньше памяти и остаётся на будущее.

Слот приложения 4 МБ остаётся 2 944 КиБ, A/B-обновления самого хаба нет.
SoftAP и Zigbee OTA этим изменением не добавляются. В уже опубликованном
**0.2.0** варианты прежние: на 4 МБ MQTT отсутствует, консоль включена.

## Поддержка устройств

Спецификация (черновик, только дизайн): [`docs/device-support.md`](docs/device-support.md),
примеры определений: [`definitions/examples/`](definitions/examples/),
инструменты замеров: [`tools/herdsman-coverage/`](tools/herdsman-coverage/),
прототип компилятора: [`tools/zdefc-proto/`](tools/zdefc-proto/).

- **Три уровня, ни один не требует перепрошивки хаба.** (a) Generic ZCL: после
  interview хаб сам создаёт сущности из стандартных кластеров (On/Off, Level,
  Color, датчики, IAS, метеринг, батарея, термостат, шторы, замки…) и
  настраивает binding/reporting, как ZHA. (b) Декларативные определения
  (данные, а не код): совпадение по производителю/модели/отпечатку (в том числе
  по маске), атрибуты производителя, датапоинты Tuya EF00, команды/события и
  небольшой язык выражений, компилируемый в проверяемый байткод без циклов.
  (c) YAML → детерминированный CBOR с хешем; YAML компилируется только на
  клиенте (CLI и WASM в UI), хаб принимает CBOR; генератор из
  zigbee-herdsman-converters выдаёт отчёт о покрытии.
- **Приоритет слоёв:** пользовательское определение > самоописание устройства >
  каталог > generic; каталог может понизить самоописание у заведомо
  неисправной прошивки.
- **Каталог:** отдельный репозиторий `faronov/zigbee-rs-definitions`, релизы
  GitHub (манифест, 256 шардов, банки для 4 МБ и 8 МБ), подпись Ed25519 ключом
  из секретов GitHub Actions. В банк для 4 МБ попадают только полностью
  переведённые определения, отобранные по популярности (упоминания модели в
  issues Z2M/ZHA, `tools/herdsman-coverage/popularity.py`); на платах 4 МБ
  дополнительно 64 КиБ под пользовательские и скачанные определения, на 8 МБ —
  банки 2 × 576 КиБ и 128 КиБ локальных определений.
- **zigbee-rs использует manufacturer code 0x6D6B** (регистрация в CSA не
  планируется, риск коллизии описан): кластер самоописания Device Schema
  0xFC6B, настройки 0xFC6C. Схема отдаётся кусками по 48 байт через обычный
  Read Attributes и генерируется при сборке из `#[derive(ZclSettings)]`.
- **Green Power:** синк работает на NCP (`NCP_SINK`, уровень безопасности 0x00
  с предупреждением в UI для незащищённых GPD); хаб разбирает `EVT_GP_*`:
  идентификация по SrcID/DeviceID/Manufacturer+Model ID, generic-уровень GP,
  GP-определения (FlowerX GP, BGT1 GP, GP-датчик и выключатель zigbee-rs),
  таблица Model ID под 0x6D6B; каждый отчёт обновляет last_seen и состояние.
  Трансляция на NCP — только возможный будущий локальный запасной путь.
- **Модель сущностей один-в-один с Home Assistant** (платформы, device/state
  class, единицы, config/diagnostic), чтобы будущая интеграция HA была тонким
  мостом.
- **Замерено** на zigbee-herdsman-converters 26.130.0 (4 664 определения):
  55,1 % полностью декларативны (generic 41,7 % + Tuya 13,4 %), ещё 26,1 %
  требуют вендорских шаблонов (порядок: Hue light — один шаблон закрывает 583,
  затем Lumi, затем специфика Tuya), 18,8 % — произвольный JS. Таблицы DP Tuya
  декларативны на 79 %.
- **Размеры:** простые определения — 120–320 Б CBOR; банк 256 КиБ вмещает
  ~2 000 сжатых определений (~83 Б на определение в deflate-блоке, всего
  ~226 КиБ); на 8 МБ банк 576 КиБ вмещает всё переводимое (~365 КиБ).
- **Движок** ([`crates/hub-devices`](crates/hub-devices/README.md), пока
  только хост-тесты): опрос → отпечаток → разрешение слоёв → сущности со
  стабильными uid `<device>:<endpoint>:<key>`, generic-уровень ZCL с
  умолчаниями отчётов, определения в виде CBOR от zdefc через `zdef`
  (выражения на VM zdef), Tuya EF00 с синхронизацией времени и magic packet,
  самоописание через чанки ZRDS, Green Power (generic-уровень, GP-определения,
  GP-привязки на устройстве через ZRHP 0x0A08–0x0A0D или на хабе),
  доступность, события и модель WebSocket API. Движок sans-IO за трейтом
  `ZigbeeTransport`; адаптер к хост-ядру этапа 1 — следующий шаг.

## Выбор фреймворка: esp-idf-svc (`std`), а не esp-hal

Хабу на S3 нужны: Wi-Fi и Ethernet W5500, TLS, HTTP-сервер с переходом на
WebSocket, куча в PSRAM, NVS/OTA, USB-стек устройства и драйвер UART с приёмом
через IRAM/DMA. В ESP-IDF всё это есть в виде поддерживаемых компонентов,
используемых в продуктах (`esp_wifi`, драйвер W5500 в `esp_eth`, mbedTLS,
`esp_http_server` с поддержкой WebSocket, malloc из SPIRAM, `app_update`,
TinyUSB, драйвер UART с `CONFIG_UART_ISR_IN_IRAM`), а esp-idf-svc даёт к ним
безопасный доступ из Rust со `std` (потоки, `std::sync`, `std::net`). У
`zigbee-zrhp` уже есть фича `std` именно для такого хоста. esp-hal + embassy
привлекательны (без C, async), но WebSocket-хаб пришлось бы собирать из более
молодых крейтов: Wi-Fi (esp-radio), W5500 (embassy-net-wiznet), TLS и
HTTP/WS-сервер. Поэтому практичная основа — esp-idf-svc. Тот же выбор записан
в спецификации ZRHP (12.4).

## Факты о плате (сверены с источниками Espressif)

Источники: документация esp-thread-br «Hardware Platforms» (распределение GPIO)
и схема платы v1.3 (`esp_thread_br_zigbee_gw_schematics_v1.3.pdf`, блок
«Interface»). Обе совпадают с таблицей в спецификации ZRHP:

| Сигнал | S3 | Связь | H2 |
|---|---|---|---|
| UART S3 TX → H2 RX | GPIO18 | R17 | GPIO23 (U0RXD) |
| UART S3 RX ← H2 TX | GPIO17 | R16 | GPIO24 (U0TXD) |
| Сброс H2 | GPIO7 | R14 | EN (подтяжка R2 10 кОм, C5 1 мкФ) |
| Стрэп загрузки H2 | GPIO8 | R15 | GPIO9 (кнопка + внутренняя подтяжка; у GPIO8 подтяжка R3 10 кОм) |
| PTA request / priority / grant / tx_line | GPIO12 / 10 / 13 / 11 | R23 / R21 / R24 / R22 | GPIO0 / 2 / 1 / 3 |
| Резерв (запаяны, проверено в обе стороны; используются для RTS/CTS) | GPIO6 / 5 / 4 | R18 / R19 / R20 | GPIO12 / 4 / 5 |
| W5500 (дочерняя плата, SPI2) | SCLK 21, MOSI 45, MISO 38, CS 41, INT 39, RST 40 | | |

Замерено на плате в hwlab (ранний образец):

- Флеш S3: **4 МБ** (Zbit 5e4016, SFDP подтверждает), а не 8 МБ — в таблице
  заказа Espressif указано 4 МБ «в некоторых ранних образцах»; в продаже платы
  с 8 МБ. Стоковый образ размечен под 4 МБ (ota_0/ota_1 по 1,6 МБ, `rcp_fw`
  500 КБ). Поэтому хаб должен поддерживать оба размера (см. «Разметка флеша
  S3»). PSRAM: модуль на лабораторной плате — **ESP32-S3-WROOM-1 N4R8**
  (маркировка M0N4R8: флеш 4 МБ, **8 МБ octal PSRAM** в кристалле
  ESP32-S3R8). Сборки до hub 0.1.3 поддерживали только quad PSRAM, поэтому
  плата работала без PSRAM. На других платах встречаются N4R2 (2 МБ quad, у
  пользователя), в продаже — N8R2/N8R8; смотрите маркировку модуля или
  `esptool chip-id` («Embedded PSRAM 8MB»/«2MB»).
- H2: ESP32-H2 **ревизии v0.1**, флеш **4 МБ** (GigaDevice c84016). Это
  закрывает открытый в спецификации вопрос 2 МБ/4 МБ для этой платы; NCP
  всё равно определяет размер при работе (решение N4 спецификации).
- R18, R19 и R20 запаяны (2026-11-19, `tools/flow/reserved_lines.py`):
  каждый пин S3, выставленный в 0/1, читался на H2 (ROM-загрузчик,
  `GPIO_IN`), и каждый пин H2, выставленный в 1/0, читался на S3.
- Стоковые прошивки: `esp_ot_br` в ota_0 на S3; `esp_ot_rcp` (OpenThread RCP,
  собран под 2 МБ) на H2 и его копия в разделе `rcp_fw` на S3.

### Разметка флеша S3

S3 **не хранит образы NCP**: откат NCP живёт на H2 (A/B-слоты приложения,
`FW_*` в неактивный слот, пробная загрузка, `FW_CONFIRM`, откат загрузчиком
H2; решение ZRHP N6 с поправкой от 2026-11-18).

**Продукт — платы с 8 МБ** (решение от 2026-11-20): два слота приложения по
3 МиБ с A/B OTA и один раздел данных. **Ранние образцы с 4 МБ** (плата
hwlab) получают **разработческую разметку**: один слот приложения, без OTA
(прошивка и восстановление через hwlab / USB-Serial-JTAG), мост этапа 0
остаётся отдельным образом для работы с H2. Хаб определяет размер флеша при
загрузке и проверяет, что таблица ему соответствует (`hub_core::layout`):
таблица хаба для другого размера или разделы за концом флеша — фатальная
ошибка (хаб не запускается); чужая таблица (штатная, на время запуска) —
работа с хранилищем хоста в RAM. Таблицы: `firmware/hub/partitions-8mb.csv`,
`partitions-4mb-dev.csv`; бинарники — `tools/make-partition-table.sh`.

| Раздел | 8 МБ, продукт | 4 МБ, разработка |
|---|---|---|
| загрузчик | 0x000000, 32 КиБ | так же |
| таблица разделов | 0x008000, 4 КиБ | так же |
| `nvs` (Wi-Fi, калибровка PHY, мелкие настройки) | 0x009000, 24 КиБ | так же |
| `otadata` | 0x00F000, 8 КиБ | — |
| `phy_init` | 0x011000, 4 КиБ | 0x00F000, 4 КиБ |
| дамп ядра | 0x012000, 56 КиБ | 0x2F0000, 64 КиБ |
| приложение хаба | `ota_0` 0x020000 и `ota_1` 0x320000, **по 3 МиБ** | `factory` 0x010000, **2 944 КиБ** |
| `hubdata` (журнальное хранилище) | 0x620000, 1 920 КиБ | 0x300000, 1 МиБ |

`hubdata` разработческой разметки вмещает области на 896 КиБ из
device-support 16.1 (журнал хранилища ZRHP-хоста 128 КиБ, конфигурация
32 КиБ, база конвертеров 2 × 256 КиБ, локальные определения 64 КиБ) и
запас. CI проверяет приложение хаба на оба слота (3 МиБ и 2 944 КиБ); сборка
с приложением — 2,1 МиБ (см. «Этап 2»). Штатный `esp_ot_br` занимает 1,6 МБ
*вместе* с OpenThread, который хабу не нужен.

**База конвертеров.** Определения устройств — декларативные данные,
обновляются без OTA приложения: компактные CBOR-записи (идентификаторы модели
и производителя, сущности, сопоставление кластеров/атрибутов, масштабирование
значений и таблицы enum, reporting и ссылки на generic-обработчики,
скомпилированные в приложение). Кода в базе нет. Оценка вместимости одного
банка 256 КиБ со словарями ключей, вендоров и идентификаторов обработчиков и
индексом примерно 18 Б на определение:

| Вид определения | Размер CBOR | В банке, без сжатия | В банке, deflate по блокам 4 КиБ (≈ 2–2,5×) |
|---|---:|---:|---:|
| Простое (лампы, розетки, датчики на стандартных кластерах) | 150–250 Б | ~1 000–1 500 | ~2 500–3 500 |
| Сопоставления датапоинтов в стиле Tuya | 600–1 200 Б | ~200–400 | ~500–1 000 |
| Реальная смесь (в среднем ≈ 300 Б) | | **~800** | **~1 600–2 000** |

Полный каталог zigbee-herdsman-converters (≈ 4 500+ определений, примерно
1,3–1,5 МБ без сжатия) не помещается на плату с 4 МБ даже сжатым и в двух
банках. На 4 МБ — отобранный набор плюс определения, скачиваемые по требованию
для сопряжённых устройств (в доме редко больше ~100 разных моделей). На 8 МБ
(`hubdata` 1 920 КиБ) весь каталог помещается сжатым, в двух банках.

**Вариант (не решено): свободный флеш H2 как хранилище хоста через ZRHP BULK.**
При разметке H2 на 4 МБ из спецификации (два слота по 1,875 МиБ) свободного
места почти нет; ~1,8–2 МБ освобождаются, только если на H2 с 4 МБ оставить
слоты по 896 КиБ–1 МиБ.

- Плюсы: около 2 МБ дополнительно без изменения железа; переживает
  перепрошивку хаба и изменение разделов S3; можно хранить каталог
  конвертеров, бэкапы или логи; флеш S3 остаётся под приложение.
- Минусы: данные хаба зависят от NCP (перепрошивка через ROM, замена чипа или
  смена разметки могут их потерять); 460 800 бод — это около 40 КБ/с, общие с
  трафиком Zigbee и кредитами, поэтому для произвольного доступа нужен кэш на
  S3; стирание флеша на одноядерном H2 останавливает выборку из флеша и может
  нарушить тайминги MAC; в спецификации понадобятся новый тип объекта BULK,
  согласование ёмкости и правила на случай пропадания питания; только для
  модулей H2 на 4 МБ; не переносится на другие NCP.

## Этап 0: `tbr-bridge`

### Почему USB OTG, а не USB-Serial-JTAG

Блок USB-Serial-JTAG (USJ) на S3 не сообщает прошивке состояние DTR/RTS и
параметры линии (в карте регистров S3 их нет; в C6/H2 их добавили), а FIFO
его CDC-эндпоинта — 64 байта. Поэтому мост работает на контроллере USB OTG
S3 с TinyUSB (`espressif/esp_tinyusb` 1.7.6), который сообщает
SET_CONTROL_LINE_STATE и SET_LINE_CODING. Оба делят один внутренний USB PHY на
разъёме USB2, поэтому **пока работает мост, USJ (а с ним и доступ hwlab к
JTAG/флешу S3) пропадает** — см. «Восстановление».

### USB-интерфейс

VID 0x303a, PID 0x4002, серийный номер = заводской MAC S3 (например,
`7CDFA1FE67F0`). macOS называет порты по серийному номеру и номеру интерфейса:

| Порт (на этой плате) | Назначение |
|---|---|
| `/dev/cu.usbmodem7CDFA1FE67F01` | CDC 0: прозрачный мост к UART H2 |
| `/dev/cu.usbmodem7CDFA1FE67F03` | CDC 1: консоль управления (текст, любая скорость) |

CDC 0:

- Байты проходят в обе стороны. H2 → хост: драйвер UART с прерыванием в IRAM,
  приёмное кольцо 16 КиБ, порог RX FIFO 64 Б и таймаут 2 символа, читает поток
  с приоритетом 20 в TX FIFO TinyUSB 4 КиБ. Хост → H2: RX FIFO TinyUSB (4 КиБ)
  → передающее кольцо UART 8 КиБ; когда оно заполнено, мост перестаёт читать
  и USB отвечает хосту NAK (обратное давление, без потерь).
- Параметры линии от хоста задают скорость UART, число бит данных, чётность и
  стоп-биты (применяются только при изменении, см. «Статус»).
- DTR/RTS управляют H2 как классическая схема автосброса esptool:
  `EN low = RTS && !DTR`, `BOOT low = DTR && !RTS`; (0,0) и (1,1) оставляют H2
  работать, поэтому открытие порта (обе линии выставлены) и его закрытие
  никогда не сбрасывают H2. EN и BOOT — открытый сток с подтяжками, поэтому
  не конфликтуют с кнопками H2. Отключить сопоставление можно командой
  консоли `lines off`, если хост дёргает линии модема для других целей.
- После каждого сброса ROM H2 печатает лог загрузки на 115 200; стоковый RCP и
  ZRHP NCP затем работают на 460 800 8N1.
- Аппаратное управление потоком (RTS/CTS) **включено по умолчанию** с 0.2.0,
  см. «Управление потоком UART». Когда оно включено и порт на хосте открыт,
  данные H2 → хост не теряются: мост ждёт хост, а RTS приостанавливает H2.

Консоль (CDC 1): `help`, `info` (скорость, формат кадра, уровни EN/BOOT,
счётчики байт и потерь), `h2 reset`, `h2 boot` (ROM-загрузчик: BOOT low,
импульс EN 20 мс, BOOT отпускается через 100 мс после EN), `h2 hold` /
`h2 release`, `baud <rate>`, `lines on|off`, `flow on|off`, `stats reset`,
`gpio` / `gpio <4|5|6> high|low|in|pu|pd` (тестовый доступ к резервным
линиям; выключает flow), `diag` (метки потоков и последний перезапуск
супервизором), `s3 usj` (синоним `s3 download`: вернуть USB PHY в
USB-Serial-JTAG, приложение продолжает работать с выключенным мостом),
`s3 reset`. `info` показывает также пины управления потоком и счётчики
переполнений RX FIFO, заполнения кольца, ошибок кадра и чётности UART.

Поток-супервизор перезапускает S3, если цикл консоли стоит 15 с или колбэк
TinyUSB застрял в коде моста на 5 с; перед этим он сохраняет метки и
состояния задач FreeRTOS в RTC-память для `diag`.

### Управление потоком UART (RTS/CTS)

Резервные перемычки 0 Ом несут аппаратное управление потоком (все запаяны,
см. «Факты о плате»):

| Сигнал | S3 | Связь | H2 |
|---|---|---|---|
| S3 RTS → H2 CTS | GPIO4 (RTS UART1) | R20 | GPIO5 (U0CTS через матрицу GPIO, подтяжка вниз) |
| H2 RTS → S3 CTS | GPIO5 (CTS UART1, подтяжка вниз) | R19 | GPIO4 (U0RTS через матрицу GPIO) |
| запасная | GPIO6 | R18 | GPIO12 |

- S3: ESP-IDF `uart_set_hw_flow_ctrl(CTS_RTS)`, RTS снимается при 100 из
  128 байт RX FIFO. На CTS подтяжка вниз, поэтому прошивка H2 без управления
  потоком (пин не управляется) никогда не блокирует передачу S3. `flow off`
  держит RTS S3 в 0 («готов») и игнорирует CTS.
- H2 (что настраивает BR-вариант NCP): U0RTS на GPIO4, U0CTS на GPIO5 с
  подтяжкой вниз, `rx_flow_en` с порогом около 96 байт, `tx_flow_en`. Оба
  GPIO — входы в ROM-загрузчике H2 и не являются стрэпами (даташит ESP32-H2
  v1.3: GPIO8, GPIO9, GPIO25), так что esptool через мост работает как
  раньше. GPIO4/5 — это площадки MTCK/MTDI; JTAG на площадках по умолчанию
  не выбран (выбран USB-JTAG), так что использовать их как GPIO ничего не
  стоит.

**Замеры** (2026-11-19, мост 0.2.2, `tools/flow/flow_test.py`; на H2
работает тестовая программа только в RAM, загруженная через ROM-загрузчик,
во флеш H2 ничего не пишется; передачи по 256 КиБ, 128 КиБ для случая с
остановками):

| Скорость | Flow | S3→H2 поток | S3→H2, H2 стоит 30 мс каждые 4 КиБ (прерывания выключены) | H2→S3 поток | H2→S3, хост пауза 1 с каждые 32 КиБ |
|---:|---|---:|---|---:|---|
| 460 800 | выкл | 43,8 КиБ/с, 0 потерь | **потеряно 30 018 Б** (27 переполнений FIFO) | 45,1 КиБ/с, 0 потерь | 0 потерь |
| 460 800 | вкл | 43,9 КиБ/с, 0 потерь | **0 потерь**, 33,9 КиБ/с | 45,1 КиБ/с, 0 потерь | 0 потерь |
| 921 600 | выкл | 87,8 КиБ/с, 0 потерь | **потеряно 50 063 Б** (20 переполнений) | 90,2 КиБ/с, 0 потерь | 0 потерь |
| 921 600 | вкл | 87,6 КиБ/с, 0 потерь | **0 потерь**, 50,5 КиБ/с | 90,2 КиБ/с, 0 потерь | 0 потерь |
| 2 000 000 | выкл | 176,0 КиБ/с, 0 потерь | **потеряно 76 296 Б** (13 переполнений) | 196,0 КиБ/с, 0 потерь | 0 потерь |
| 2 000 000 | вкл | 176,0 КиБ/с, 0 потерь | **0 потерь**, 77,3 КиБ/с | 196,0 КиБ/с, 0 потерь | 0 потерь |

- Поток идёт примерно на 95 % (H2→S3) и 88 % (S3→H2, планирование USB) от
  скорости линии; UART S3 ни разу не переполнился (`info`: 0 переполнений
  FIFO, 0 потерь, 0 ошибок кадра за все прогоны).
- Без управления потоком H2, который не читает 30 мс, теряет данные на любой
  скорости (его RX FIFO — 128 байт: 2,8 мс на 460 800, 0,64 мс на 2 Мбод).
  С RTS/CTS ничего не теряется, S3 просто ждёт.
- Случай с паузой хоста не теряет данные в обоих режимах: macOS продолжает
  читать CDC-эндпойнт в буфер tty, пока приложение спит, поэтому до S3
  пауза не доходит. Остановка на стороне S3 покрыта конструкцией (мост ждёт
  хост, кольцо 16 КиБ заполняется, RTS приостанавливает H2), но не измерялась.


### Прошивка H2 через мост (для работы zrhp-ncp)

Порт `/dev/cu.usbmodem7CDFA1FE67F01`, сброс esptool по умолчанию (у моста не
PID 0x1001, поэтому esptool использует классическую последовательность
DTR/RTS (classic/UnixTight), которую мост переводит в EN/BOOT). ROM
синхронизируется на 115 200, затем esptool переключается на скорость из `-b`:

```sh
esptool --chip esp32h2 --port /dev/cu.usbmodem7CDFA1FE67F01 flash-id
esptool --chip esp32h2 --port /dev/cu.usbmodem7CDFA1FE67F01 -b 460800 \
  write-flash --flash-size 4MB 0x0 bootloader.bin 0x8000 partition-table.bin 0x10000 app.bin
# --after hard-reset (default) boots the new image: RTS pulse with DTR released.
```

Эквивалент вручную (порт консоли): `h2 boot` → протокол ROM на 115 200 через
CDC 0 → `h2 reset` для обычной загрузки. Затем откройте CDC 0 на 460 800
(pyserial по умолчанию ставит DTR=RTS=1, сброса нет) для работы с NCP;
`h2 reset` или импульс RTS при DTR=0 сбрасывает NCP.

Сначала сделайте бэкап: стоковый образ H2 лежит в
`~/.hwlab/artifacts/esp-thread-br-h2-backup/`.

### Сборка

Xtensa Rust из espup. На macOS Intel последний релиз со сборкой
`x86_64-apple-darwin` — 1.90.0.0.

```sh
cargo install espup ldproxy --locked
espup install --toolchain-version 1.90.0.0 --targets esp32s3 --std
. ~/export-esp.sh
cd firmware/bridge && cargo build --release      # downloads ESP-IDF v5.5.1 into .embuild
cd ../.. && tools/make-app-image.sh              # -> target/tbr-bridge-app.bin
cargo test                                       # host tests: hub-core, hub-ncp, hubctl (stable Rust)
```

### Прошивка S3 (только hwlab, без кнопок)

Этап 0 сохраняет стоковые таблицу разделов и загрузчик и заменяет только
**ota_0 по адресу 0x20000** (otadata уже выбирает ota_0). Проверенный цикл
(0.1.2 → 0.1.3, 2026-11-18):

1. Консоль моста: `s3 usj` (или `s3 download`, или `stty -f
   /dev/cu.usbmodem7CDFA1FE67F03 1200`). Порты моста исчезают, примерно через
   1 с появляются `espusbjtag/303a:1001:7C_DF_A1_FE_67_F0` /
   `uart/cu.usbmodem1474301`. Приложение продолжает работать с выключенным
   мостом.
2. Защита записи в hwlab требует проверенный бэкап, совпадающий с текущим
   флешем, поэтому сначала снимите его (оба ядра на это время
   останавливаются), затем прошивайте:

   ```sh
   hwlab target flash backup --yes --device espusbjtag/303a:1001:7C_DF_A1_FE_67_F0 --arg dir=$DIR
   hwlab target flash program --yes --device espusbjtag/303a:1001:7C_DF_A1_FE_67_F0 \
     --config allow_flash=true --config allow_erase=true \
     --arg path=$HOME/.hwlab/artifacts/zigbee-rs-hub/tbr-bridge-<ver>-app.bin --arg address=0x20000 \
     --arg confirm=program-flash --arg backup=$DIR/esp-flash-5e4016-4096K-<sha>.bin
   ```
3. Запустите её сбросом через RTS USJ с помощью плагина `uart` в hwlab (MCP):
   `capture_start` на `uart/cu.usbmodem1474301` (115200, без настроек
   `dtr`/`rts`), затем `device_invoke uart SerialTransport.set_lines
   {dtr:false, rts:false}`. Открытие порта выставляет обе линии; сброс DTR
   первым проходит как (DTR=0, RTS=1) = сброс, а отпускание RTS загружает
   приложение. Порт USJ пропадает, порты моста возвращаются. (hwlab запрещает
   сброс SoC на S3, поэтому это единственный сброс без кнопок.)

Через **MCP**-сервер hwlab образ хаба (2,4–2,5 МБ) за один вызов не
прошивается: запись идёт со скоростью около 11 КБ/с, а запрос MCP
обрывается примерно через 110 с, оставляя наполовину записанный слот
(проверено 2026-11-21). Прошивайте по частям: образ начиная со смещения
0x1000 — сырыми частями не больше 640 КиБ (`raw: true`, по адресам 0x11000,
0xB0000, …), затем снимите свежий бэкап и прошейте весь образ по 0x10000;
hwlab пропускает совпадающие секторы, так что записывается только сектор
заголовка (около 40 с). Не делайте перед этим `halt` работающего
приложения: из-за остановленного ядра срабатывает сторожевой таймер, и S3
перезагружается.

**Не перезагружайте S3 в ROM download mode из прошивки.**
`RTC_CNTL_FORCE_DOWNLOAD_BOOT` (0x6000812C, бит 0) переживает сбросы чипа
через USJ (`rst:0x15`), и ROM S3 его не снимает. Мост 0.1.0–0.1.2 использовал
его для `s3 download`, и после этого каждый сброс через RTS приводил к
`boot:0x23 DOWNLOAD`. Если такое случилось: пока S3 в ROM-загрузчике,
отправьте загрузчику `SYNC`, затем `WRITE_REG 0x6000812C = 0` через плагин
`uart` hwlab (`SerialTransport.write`, SLIP-кадры), потом сделайте сброс
через RTS. Сделано один раз 2026-11-18. Тот же симптом после BOOT + RESET
даёт защёлкнутый стрэп загрузки; его снимает только обычный RESET или
отключение питания. Для ROM download mode без кнопок используйте
последовательность esptool для USJ (DTR=1/RTS=0, затем DTR=0/RTS=1, затем обе
в 0) — она не залипает.

### Восстановление (как вернуть hwlab доступ к S3)

Биты маршрутизации PHY находятся в RTC_CNTL и переживают программный сброс и
сброс после паники, поэтому мост явно возвращает PHY в USJ:

| Путь | Результат |
|---|---|
| консоль `s3 usj` / `s3 download` или порт консоли на скорости 1200 | PHY → USJ, приложение продолжает работать с выключенным мостом (проверено) |
| USB не определился за 20 с после загрузки | PHY → USJ |
| загрузка после паники или сброса сторожевым таймером | сохранённый режим хаба: хаб перезапускается (`info` показывает панику и серию сбоев); режим моста или четвёртый сбой подряд, каждый в первые 10 мин после загрузки: безопасный режим, TinyUSB не запускается, PHY → USJ |
| отключение питания или S3 BOOT + RESET | холодная загрузка / ROM download на USJ |

При возврате хост видит настоящее отключение и новое подключение. Мост
снимает подтяжку D+ (TinyUSB `tud_disconnect` + принудительные подтяжки) на
500 мс, переключает PHY и возвращает регистры подтяжки USJ в состояние после
сброса (`DP_PULLUP` = 1, без принудительного режима).

## Этап 1: ZRHP-хост (`hub-ncp`, `hubctl`, `tbr-hub`)

Одно ядро хоста в двух местах: на macOS с настоящим NCP через мост
(быстрый цикл разработки) и на S3, который говорит с UART1 напрямую.

```text
 hubctl (macOS)  ── serial ── tbr-bridge CDC 0 ── UART ──┐
                                                         ├── H2: ZRHP NCP
 tbr-hub (S3, hub mode) ── UART1 921 600 RTS/CTS ────────┘
      both: hub-ncp = driver (zigbee-zrhp Link) + lifecycle (Hub) + store
```

### `crates/hub-ncp`

| Часть | Что делает |
|---|---|
| `transport` | `PortRx` (поток чтения) / `PortTx` (драйвер: запись, скорость линии, RTS/CTS), `NcpControl` (EN/BOOT), канал в памяти |
| `driver` | Один поток владеет `zigbee_zrhp::link::Link<8, 8>` (встроенный профиль: окно приёма 8, кредит LOG 0, BULK 2; кредиты возвращаются при доставке). На `EVT_NCP_READY` он сам отвечает `SYS_NEGOTIATE` + `SYS_GET_INFO` и затем сообщает о сессии. Запросы **придерживаются**, пока жизненный цикл не восстановил NCP (не дольше бюджета восстановления 20 с). При потере сессии уже отправленные запросы становятся «под вопросом»: тот же cookie NCP (`PEER_RESYNC`) ⇒ повтор с тем же TID и флагом `RETRY` (отвечает кэш повторов NCP), новый cookie ⇒ `LINK_RESET` (доставка неизвестна, спец. 6.5). Двухфазные команды ждут своего завершающего события (`EVT_APS_DATA_CONFIRM`, `EVT_NETWORK_STATE`). Без сессии драйвер перебирает 921 600 + RTS/CTS → 460 800 без управления потоком |
| `lifecycle` (`Hub`) | Бесшовное восстановление в каждой сессии: несовпадение управления потоком UART (NCP без RTS/CTS ⇒ хост выключает своё), идентичность хранилища (`ncp_ieee`), cookie NCP, `table_epoch`, размер флеша NCP (`SYS_GET_INFO.flash_size`, решение N4: по нему выбирается размер слота H2 — 1,875 МиБ на 4 МБ, 896 КиБ на 2 МБ, — и слишком большие образы отклоняются ещё до `FW_BEGIN`); владение сетью (сеть NCP принимается в пустое хранилище, чужая сеть не трогается, потерянная — сообщается); `NWK_INIT` с полами из журнала контрольных точек (`последняя + 9 × fc_stride`); повтор хост-эндпоинтов и остатка открытого присоединения; `TBL_SYNC`; проверка прошивки NCP. Операции: `form` (PAN ID, EPID и ключ выбирает и сохраняет хаб, затем `NWK_FORM`), `permit_join`, `add_endpoint`, `send_aps`, `fw_update`, `fw_confirm`, `reset_ncp` (программный / EN), `enter_rom_loader`. Обслуживание (`netops`): `energy_scan`, `change_channel` (хранилище следует за новым каналом и update ID), `set_tx_power` (сохраняется и повторяется при каждом восстановлении), `diag_counters`, `ncp_status`, таблицы соседей/маршрутов/детей координатора (все страницы), `backup_export` / `backup_restore` (потоки записей ZRHP, спецификация 9; восстановленная сеть принимается во владение, её счётчики становятся полами), `leave_reset` |
| `inventory` | Устройства, которые NCP уже знает: `TBL_READ` таблицы `DEVICE`, `DIAG_GET_CHILDREN` и `DIAG_GET_NEIGHBORS` (постранично; бывшие дети пропускаются; `UNSUPPORTED_COMMAND` допускается и сообщается), объединённые по IEEE с записями устройств хранилища, без самого координатора |
| `fw` | `FW_BEGIN` → `FW_WRITE` (две в полёте, синхронизация по `next_offset`) → `FW_FINISH` → `FW_ACTIVATE`, прямо из источника (файл, загрузка); S3 образов NCP не хранит. Следующая сессия подтверждает собственный пробный образ хаба командой `FW_CONFIRM` после восстановления сети или сообщает об откате загрузчиком H2. Пробные образы, активированные не этим хабом, не подтверждаются (ими может владеть другой хост) |
| `store` | Журнал хранилища хоста (спец. 3.4/8.8): кольцо 32 × 4 КиБ, записи `len, type, commit, payload, CRC-32C`, фиксация сбросом байта commit после контрольного чтения; снимок в двух поколениях + дельты, уплотнение при заполнении больше половины кольца. Хранит идентичность хранилища, свою сеть (с ключом), журнал контрольных точек FC (сохраняется каждая 4-я), реестр устройств, ожидающее обновление NCP и хост-эндпоинты. Носители: раздел `hubdata`, файл, RAM |
| `sim` | Симулированный NCP (настоящий линк на стороне NCP, сценарный набор команд с A/B-слотами, пробной загрузкой и откатом, энергосканированием, сменой канала, мощностью передатчика, таблицами и счётчиками DIAG, экспортом/восстановлением бэкапа, удалёнными роутерами, отвечающими на Mgmt_Lqi/Mgmt_Rtg; любую команду можно сделать `UNSUPPORTED_COMMAND`) для тестов и `hubctl --sim` |

Этап 1 выставляет `FC_CHECKPOINTS | RETRY_CACHE`, но не `HOST_TABLES`
(таблицы на стороне хоста и ключи связи — этап 2): на `TBL_LOOKUP` хаб
отвечает `NOT_FOUND`, на `TBL_WRITEBACK` — `STORAGE_ERROR`.

### `tbr-hub` (S3)

| Режим | Что работает |
|---|---|
| **мост** (по умолчанию; ключа в NVS нет) | `tbr-bridge` 0.2.4 без изменений: та же USB-идентичность и порты, мост на CDC 0, консоль на CDC 1 |
| **хаб** | `hub-ncp` на UART1 (921 600 + RTS/CTS, ISR в IRAM, кольцо приёма 16 КиБ), EN/BOOT H2 на GPIO7/8; CDC 0 не используется; консоль на CDC 1 с командами `hub …`; команды моста, трогающие UART или EN/BOOT H2, отклоняются |

Новые команды консоли: `mode`, `mode bridge|hub` (сохраняется в NVS
`hub/mode`, перезагрузка), `mode hub once` (одна загрузка в режиме хаба,
любой следующий сброс возвращает сохранённый режим), `hub [status]`,
`hub echo [n]`, `hub form [channel]`, `hub permit <s>`, `hub fw slots`,
`hub fw confirm`, `hub ncp reset [hard]`, `hub crash` (намеренная паника),
`hub rom` (ручное восстановление
NCP: перезагрузка в мост с H2 в ROM-загрузчике, дальше esptool на CDC 0 с
образом от оператора). Восстановление USB (`s3 usj`, «касание» 1200 бод,
таймаут энумерации, безопасный режим после сбоя) — от моста, в обоих режимах;
сохранённый хаб после сбоя перезапускается и уходит в безопасный режим только
при циклических сбоях. Вернуться к мосту: `mode bridge` в консоли (CDC 1)
или `s3 usj` и перепрошивка.

Хранилище хоста использует раздел `hubdata`, если он есть в таблице
(`firmware/hub/partitions-4mb.csv`, `partitions-8mb.csv`; разметки 4 МБ /
8 МБ выше), и проверяет, что таблица помещается в обнаруженный флеш; со
штатной таблицей платы hwlab оно работает в RAM. Прошивка новой таблицы
разделов — отдельный явный шаг.

### `hubctl` (компьютер)

```sh
cargo run -p hubctl -- --sim status                     # simulated NCP
cargo run -p hubctl -- --sim form --channel 17
hubctl --serial /dev/cu.usbmodem7CDFA1FE67F01 --read-only status   # real NCP, observe only
hubctl --serial … --store hubdata.bin form --channel 17            # store in a file
hubctl --serial … fw-update ncp.bin --version 0x00010100           # stream, trial boot, confirm
hubctl --serial … soak 60                                          # echoes across NCP resets
```

`--read-only` не отправляет ничего, что меняет NCP: только рукопожатие,
согласование и запросы на чтение (без `NWK_INIT`, `TBL_SYNC` и повтора
настроек). Мост следует скорости хоста и сам делает RTS/CTS в сторону H2.

## Этап 2: приложение на ядре хоста (`hub-app`, ветка `stage2`)

Движок устройств (`hub-devices`) работает на ядре ZRHP-хоста (`hub-ncp`):

| Часть | Что делает |
|---|---|
| `convert` | События ZRHP → входы движка (APS-индикации с IEEE источника и группой, принятые присоединения, `EVT_GP_*` вместе с записями sink после ввода и удалёнными таблицами sink/трансляций); APS/GP-запросы движка → протокол (`APS_DATA_REQUEST`, `GP_*` 0x0A01–0x0A0D) |
| `transport` | `ZigbeeTransport` движка поверх `hub_ncp`: APS-данные без блокировки (`Client::start`, придерживаются на время восстановления NCP, исходы считаются), GP/группы/удаление/permit join — вызовами и только при готовой сессии |
| `registry` | Реестр устройств в журнале хранилища хоста (device-support 16.1): `dev/<id>` — сжатый JSON `DeviceSnapshot` (идентичность, отпечаток, дескрипторы, поддержка атрибутов и значения, которые читает разрешение, фрагмент самоописания как zdef CBOR, настройки пользователя и переопределения сущностей, хэш и результаты настройки, запись GP sink), `udef/<id>` — пользовательские определения. Запись при изменении устройства (объединение за 2 с) и проходом раз в 30 с; одинаковые значения не пишутся, а в снимке нет измеренных значений, поэтому отчёты флеш не трогают. Значения больше 2000 Б журнал хранит частями и применяет только целиком |
| `laststate` | Последние известные значения (`st/<id>`: состояния сущностей, `last_seen`, LQI, RSSI; 0,2–0,5 КБ на устройство): устройство пишется не чаще раза в 15 мин, если изменились его состояния, раз в 6 ч, если изменились только диагностические значения, и всё сразу при чистой перезагрузке или остановке; при запуске восстанавливается с `attributes.restored: true` до следующего отчёта (веб-интерфейс показывает их бледными, HA получает атрибут) |
| `app` | Один поток: движок, сессии `ApiServer` (любой `SessionSink`), реестр, тик 1 с; один раз регистрирует эндпоинт хаба 1 (профиль HA; `hub-ncp` повторяет его при каждом восстановлении) и IEEE координатора; встроенный каталог — примеры определений, пока не установлен банк (хранилище и сервис каталога — `catalog`); раз в сессию NCP импортирует устройства, которые знает NCP, но не движок (присоединились до того, как хаб принял сеть), и опрашивает их; после старта один раз читает ещё неизвестные состояния восстановленных устройств (`refresh_unknown`; спящее устройство получает чтения сразу после своего следующего кадра), так как в снимках нет измеренных значений, а устройство может слать отчёты только при изменении (датчик C6: температура — только при изменении на 0,5 °C или раз в 15 мин) |
| `catalog` | Доверенные ключи каталога определений: **слот 0** = `keys/zdef-catalog-ed25519.pub.pem` (`ff931767…63c6a2`, kid `66f64ac1cbfc9e27`), **слот 1** зарезервирован под смену ключа (преемник добавляется в релиз прошивки, каталог подписывается им, слот 0 выводится позже); `verify_manifest` / `verify_bank` (COSE_Sign1 Ed25519, `zdef`); хранилище в `hubdata` (`store`: слоты банков A/B, запись активного банка, манифест; `local`: загруженные определения; `data`: раздел, отображённый в память) и сервис (`service`: загрузка частями манифеста, банков, веб-инструментов и шардов, что клиентам скачать, API `catalog/*`); `web`: веб-инструменты на `/zdefc/` |
| `admin` | Обслуживание сети и хаба (API 1.2, device-support 14.6): энергосканирование с рекомендацией канала в стороне от собственного канала Wi-Fi хаба, смена канала, мощность передатчика, диагностика NCP, карта сети, экспорт/восстановление Open Coordinator Backup, сброс + формирование сети; через платформу — учётные данные Wi-Fi, смена API-токена, перезагрузка, режим загрузки, сведения о системе и хвост журнала. Работа с NCP идёт в фоновых потоках задач по двум полосам, по одной задаче в каждой (тяжёлая: сканирования, карта, смена канала, бэкап/восстановление/сброс; лёгкая: диагностика, мощность; иначе `busy`), так что поток приложения продолжает обслуживание |
| `jobs` | Доска задач: запущенные задачи по полосам, прогресс (оценка по времени, измеренные проходы, необязательное `EVT_SCAN_PROGRESS` от NCP), отмена, последний результат каждого вида для клиентов, подключившихся позже |
| `ocb` | `zigpy/open-coordinator-backup` v1 ⇄ потоки записей ZRHP (порядок байтов и особенности Z2M/zigpy из ZRHP 9.1); экспорт пишется сразу текстом, без дерева JSON (ради RAM) |
| `topology` | Карта сети: `DIAG_GET_NEIGHBORS`/`ROUTES`/`CHILDREN` координатора, затем Mgmt_Lqi_req/Mgmt_Rtg_req к каждому найденному роутеру, в ширину |
| `automations` | Локальные автоматизации (API 1.3, device-support 14.8): правила из триггеров (состояние сущности равно/не равно/выше/ниже/изменилось, события сущностей, в том числе пультов и команд GP, доступность устройства, расписание cron, старт хаба), условий (состояние, окно местного времени, день недели, and/or/not) и действий (команда сущности, любой разрешённый запрос API для групп/сцен, задержка, уведомление, включить/выключить правило) в потоке приложения, sans-IO через `World`; всё ограничено (правила, запуски, трассы, запуски в минуту), петли самозапуска останавливаются по причинной цепочке; задержки по монотонным часам, расписания ждут синхронизированных настенных часов; правила в журнале как `auto/<id>` (компактный JSON, формат `v` 1) |
| `platform` | `Platform` (что приложению нужно от S3 или компьютера) и `LogRing` (кольцо последних строк журнала фиксированного размера) |

В `hub-devices` добавлены `persist` (`snapshot_device` / `restore_device`) и
`ApiServer::pump_events`; в `hub-ncp` — записи ключ/значение, PTA
`coex_enable` вслед за состоянием Wi-Fi (решение N7, повторяется при
восстановлении), `group_membership`, `remove_device`, `permit_join_on`. Все
крейты zigbee-rs закреплены на одной ревизии (master `c18875b`).

**Компьютер.** `hubctl --serial … --store hubdata.bin serve [--listen
127.0.0.1:8099] [--token T] [--hubdata FILE]` запускает приложение с WebSocket JSON API
(`ws://…/`) и хранилищем каталога в образе `hubdata` на 1 МиБ (в ОЗУ без
`--hubdata`); `hubctl catalog-push URL --token T [--from URL | --dir
DIR]` загружает подписанный каталог в хаб; `hubctl ws-call URL --token T JSON…` — минимальный клиент;
`hubctl catalog-verify FILE…` проверяет банки каталога и `manifest.cose`
ключами прошивки. Везде работает `--sim`.

**S3.** `tbr-hub` (режим хаба) запускает приложение,
WebSocket API на `ws://<ip>/api` (esp_http_server, сессия на сокет,
рассылка через detached sender) после сохранения учётных данных Wi-Fi
(консоль `wifi set <ssid> <пароль>`, `wifi`, `token`, `catalog`) и тот же
API строками JSON на CDC 0, пока хост держит порт открытым (тестовый путь
без сети).
`hub/info` возвращает имя хаба, версию API, возможности, текущий `seq`,
число устройств и сущностей, а после подъёма сессии NCP — `coordinator_ieee`,
`ncp_board` и `ncp_product` (уникальный ID для интеграции Home Assistant).
S3 реализует сторону хаба в API обслуживания (1.2,
`firmware/hub/src/platform.rs`): `hub/wifi/set` сохраняет учётные данные в
NVS, и станция сразу переподключается с ними или запускается, если хаб
загрузился без них (консольная `wifi set` в режиме хаба делает то же);
`hub/token/rotate` сохраняет новый токен в NVS; `hub/reboot`;
`hub/mode/set`; `hub/system` (свободная внутренняя куча, её минимум и
наибольший блок, время работы, SSID/IP/RSSI/канал Wi-Fi, причина сброса);
`hub/logs` из кольца в 3 КиБ RAM со строками журнала Rust до уровня Info
(C-журналы ESP-IDF туда не попадают), с местным временем, когда часы
установлены. **Время:** SNTP (`esp_sntp`, по умолчанию `pool.ntp.org`, до
трёх серверов) запускается с первым подключением Wi-Fi; S3 сохраняет часы
при программной перезагрузке, поэтому после первой синхронизации время
известно уже при загрузке (`source` `rtc`). Часы движка остаются
монотонными для его таймеров; времена в API (`time`, `last_seen`, события)
становятся Unix-временем через смещение, как только время известно
(`time_synced`, `time_utc`). Конечная точка хаба обслуживает кластер ZCL
Time (0x000A: Time, TimeStatus Master|Synchronized|MasterZoneDst, TimeZone,
DstStart/End/Shift, StandardTime, LocalTime, LastSetTime) для термостатов и
часов, а запросы времени устройств Tuya (EF00 0x24) получают местное время
заданного пояса. Рекомендация канала по
энергосканированию обходит канал точки доступа. Задачи обслуживания
выполняются в одном долгоживущем рабочем потоке со стеком 12 КиБ, который
запускается вместе с приложением; задача, начатая, пока идёт другая
(чтение диагностики во время сканирования), получает свой поток, и только
если во внутренней куче есть блок под его стек и ещё 16 КиБ (иначе `busy`,
«low memory»). Раньше каждая задача получала новый поток: после 10 ч работы
на плате hwlab было свободно 51 КБ, но ни одного блока в 12 КиБ, и все
задачи падали с `job thread: Not enough space (os error 12)`, а каждый поток
к тому же оставлял около 300 Б. С рабочим потоком (hwlab, 2026-11-22) куча
не убывает при повторных задачах; задачи используют не больше 4 КиБ стека
(максимум пишется в журнал после каждой задачи); пятипроходное
сканирование при двух сессиях, читающих диагностику, проходит, лишние
чтения получают отказ «low memory». Сохранённые результаты задач занимают
не больше 8 КБ. На плате hwlab (2026-11-21) работают
`hub/system`, `hub/logs`, `hub/reboot`, карта сети (C6 как ребёнок
координатора), бэкап и смена канала 17 → 25 → 17 (около 9 с каждая, C6
перешёл следом в течение минуты); `hub/wifi/set` и `hub/mode/set` на общей
плате не проверялись. Первый вызов `network/diagnostics` там исчерпал кучу
(минимум свободной памяти 12,7 КБ, затем abort и перезагрузка: результат
строился деревом serde_json, около 0,7 КБ на объект счётчика); теперь
результаты обслуживания пишутся текстом прямо в кадр ответа с
выделением памяти, которое может не удаться (`no_space` вместо abort). После
исправления: 46 счётчиков в кадре 4 КБ за 170 мс, минимум свободной кучи
27,5 КБ, 22 КБ при сканировании карты из веб-интерфейса и трёх сессиях.

**Каталог определений.** Хаб хранит подписанный каталог
`faronov/zigbee-rs-definitions` в `hubdata`, но сам ничего не скачивает
(TLS в прошивке нет): релиз зеркалируется на GitHub Pages
(`faronov.github.io/zigbee-rs-definitions/latest/`), а клиенты с выходом в
интернет — веб-интерфейс, интеграция Home Assistant, `hubctl
catalog-push` — скачивают файлы и загружают их в хаб частями с
продолжением после обрыва (`catalog/upload_chunk` + `catalog/commit`, цели
`manifest`, `bank`, `web`, `shard`). Хаб пишет каждую загрузку потоком во
флеш (в ОЗУ — один фрагмент), проверяет её на месте (подпись Ed25519 COSE
манифеста встроенным ключом и его версия; SHA-256 из манифеста для
остальных файлов; банк — ещё и своей подписью и хешем тела, а его
определения — когда их загружает поиск) и атомарно переключает банки A/B (`hub_core::layout::HubdataMap`,
device-support 9 и 16). `catalog/status` подсказывает клиентам, что
скачать: `wants` (более новый банк под размер слота, веб-инструменты) и
`missing` (устройства, разрешённые только в generic, с шардами их ключей;
событие `definition_needed`). Шарды проверяются по установленному
манифесту, поэтому веб-интерфейс ставит более новый манифест зеркала (и
банк и веб-инструменты, которые он затем просит) до загрузки шардов — для
«Find definition», «Fetch», а при включённом `auto_update` — для
`definition_needed` и при открытии вкладки Catalog — и ещё раз после шарда,
отклонённого как несовпадающий, повторяя шарды один раз; более старый или
тот же манифест не загружается, прерванная установка банка или
веб-инструментов установленного релиза продолжается с места обрыва, а
занятому хабу — одна повторная попытка через 30 с. Поиск читает банк через отображение флеша в
память: банки формата 2 (по умолчанию в zdefc с 2026-11-21) держат во
флеше даже таблицу строк, так что поиск выделяет только распаковщик, буфер
блока на 4 КиБ и декодированных кандидатов (медиана 7,3 КБ, 33,7 КБ для
самого большого из 2 289 определений). Проверено на хосте от начала до
конца (все цели загрузки, прерванная и продолженная загрузка, перезапуск,
защита от отката, повреждённый банк; `hubctl catalog-push` установил
настоящий подписанный `catalog-2026.11.21` на симулированный хаб). На
плате BR (S3 без PSRAM, 2026-11-21) `hubctl catalog-push` установил тот же
релиз частями по 4 КиБ (банк 218 КБ примерно за 10 с, фиксация 0,6 с;
минимум свободной кучи 24 КБ при работающих Wi-Fi, NCP и подключённом
устройстве); манифест и банк переживают перезагрузку, `definitions/get`
читает банк на месте. На железе ещё не проверены загрузка веб-инструментов
и устройство, определённое по банку. Цена на S3: образ приложения
+119,5 КБ (проверка Ed25519/COSE ~32 КБ, чтение банка ~15 КБ, хранилище и
сервис загрузки ~50 КБ), статическая ОЗУ +32 Б.

**Веб-интерфейс.** `http://<ip>/` отдаёт одну статическую страницу
(`crates/hub-web/web/index.html`: HTML, CSS и JS, без фреймворков и CDN),
которая говорит только с WebSocket API на `/api`: сеть (состояние, PAN ID,
канал, расширенный PAN ID, прошивка NCP, IEEE и линк), разрешение
присоединения с обратным отсчётом, компактные карточки устройств (картинка,
имя, доступность, основные датчики, элементы управления и события —
последнее действие пульта и когда — с живыми состояниями, батарея и индикатор сигнала по LQI/RSSI; подписка на
`devices`, `entities` и `network`) и по клику на карточку — страница
устройства `#device/<id>` (модель, IEEE, NWK, LQI/RSSI, когда последний раз
виден, питание, определение — модель и источник, «partial», если каталог
перевёл его не полностью, — все сущности под заголовками разделов: датчики,
управление, события, настройки, диагностика; переименование, повторный опрос, поиск определения,
привязки, отчёты по каждому атрибуту (min и max в секундах, изменение — в
единицах сущности) и удаление с подтверждением; «назад»
возвращает к списку на прежнее место), управление выключателями и светом
(вкл/выкл, яркость), числами, списками выбора и кнопками, состояние
соединения с автоматическим переподключением; мобильная вёрстка,
светлая/тёмная тема по
`prefers-color-scheme`. Страница разбита на вкладки (`#/devices`, …):
каждый `<div class="tab" data-tab="id" data-title="…">` в `<main>`
становится вкладкой в порядке документа, а `onTab[id]` вызывается при её
показе, так что новая функция добавляет свою вкладку, не трогая остальные.
Вкладка **Green Power** (`#/gp`) открывает и закрывает окно GP-commissioning
(длительность, прокси, выход после первого сопряжения) с обратным отсчётом,
показывает GPD в двустороннем commissioning, последние отказы с причиной и
GP-устройства (ID, тип, уровень безопасности, счётчик кадров, режим sink,
значок `unsecured`, удаление с уведомлением прокси или без), управляет
GP-привязками (создание, правка, удаление, проверка; опрос цели; исполнитель
auto, device или hub; состояние по каждой цели) и уровнем безопасности и
режимом связи sink (подписка на `gp`); для неё в API 1.2 добавлены
`gp/commissioning/status` и `gp/config/get`.
Вкладка **ZCL** (`#/zcl`) — консоль для написания и отладки определений:
для устройства, конечной точки и кластера (или любого ID кластера) с
необязательным кодом производителя она читает и пишет атрибуты (тип — из
чтения, из применённого определения или вручную), настраивает и читает
репортинг, обнаруживает атрибуты и принимаемые/отправляемые команды и
отправляет любую кластерную или общую команду с hex-нагрузкой; ответы
показываются в разобранном виде. Живой поток кадров (подписка `frames`,
фильтр по кластеру) и просмотр датапоинтов Tuya EF00 (DP, тип, значение;
отправка DP) следуют за выбранным устройством; прочитанные атрибуты и
увиденные DP копируются как фрагменты определения (device-support 14.7).

Вкладка **Groups** (`#/groups`) создаёт, переименовывает и удаляет
Zigbee-группы, добавляет и убирает конечные точки-участники (ZCL Groups, с
состоянием: pending, ok, failed или ожидание пробуждения спящего
устройства), переключает световую сущность или выключатель группы (одна
групповая рассылка на команду), сохраняет текущее состояние участников как
сцену, вызывает, перезаписывает и удаляет сцены и идентифицирует группу; на
странице каждого устройства есть раздел **Bindings**: таблица привязок
устройства (чтение через Mgmt_Bind_req), ожидающие запросы и
привязка/отвязка кластеров исходной конечной точки (пресеты пульт → лампа:
On/Off, Level, Color) к конечной точке устройства или к группе (подписка на
`groups`, device-support 14.9).
Токен API страница спрашивает один раз (консоль
`token`; ссылка с `#token=…` тоже сохраняет его) и хранит в браузере.
`build.rs` при сборке построчно минифицирует страницу (отступы, пустые
строки и строки-комментарии `//` в скрипте и стилях; `src/minify.rs`
отказывается от конструкций, которые не может сохранить без изменений),
сжимает её gzip (детерминированно, на чистом Rust, без node) и вычисляет
сильный ETag (страница каждого варианта образа после gzip не больше 36 КиБ,
`hub_web::PAGE_BUDGET`, это проверяют тесты крейта); хаб отвечает
`Content-Encoding: gzip`, `Cache-Control: no-cache` и `304` при совпадающем
`If-None-Match`. `hubctl serve` отдаёт ту же страницу на `/` (WebSocket — на
`/api`), так что интерфейс можно попробовать на компьютере, в том числе с
`--sim`. В API 1.1 добавлено то, что понадобилось странице: `network/info`,
тема `network` (`permit_join`, `network_state`), поле `time` в нём для
относительного времени и `nwk` в записях устройств (device-support 14.2);
заголовок и сведения о хабе (IEEE координатора, версия API, счётчики)
берутся из `hub/info`.

**API обслуживания (1.2).** Настройки и обслуживание сети через тот же
WebSocket (device-support 14.6): `network/energy_scan` (энергия по каналам,
каналы под собственным каналом Wi-Fi хаба помечены, рекомендация),
`network/active_scan` (сети Zigbee вокруг: PAN ID, EPID, LQI, открыто ли
присоединение; сканирования и карта идут фоновыми задачами: запрос сразу
отвечает ID задачи, прогресс и результаты приходят событиями,
`network/jobs` перечисляет запущенные, `network/job/cancel` их
останавливает), `network/change_channel`, `network/set_tx_power` (повторяется после каждого
перезапуска NCP), `network/diagnostics` (состояние NCP вместе с PTA,
счётчики DIAG, счётчики кадров, счётчики линка на стороне хоста),
`network/topology` (карта из таблиц координатора и Mgmt_Lqi/Mgmt_Rtg по
эфиру), `network/backup` / `network/backup/last` / `network/restore` (Open
ZigBee Coordinator Backup в том виде, как его пишут zigpy/ZHA и Z2M;
восстановление пачками устройств на чистый NCP), `network/reset` (подтверждение
`RESET`: автоматический бэкап, выход из сети, формирование с выбранными
каналом/каналами, PAN ID, EPID, мощностью) и сам хаб: `hub/system`,
`hub/logs`, `hub/wifi/set`, `hub/token/rotate`, `hub/reboot`,
`hub/mode/set`, `hub/time` / `hub/time/set` (часовой пояс строкой POSIX TZ,
серверы SNTP). `hubctl serve` реализует сторону хаба для компьютера
(учётные данные и токен в памяти, собственный хвост журнала;
`--wifi-channel N` для рекомендации канала); `hubctl --sim --sim-demo serve`
формирует сеть на симулированном NCP с тремя роутерами, отвечающими на
Mgmt_Lqi/Mgmt_Rtg, а `--sim-unsupported 0x0106,0x0108` изображает образ NCP
без энергосканирования и управления мощностью. В веб-интерфейсе есть вкладка **Map** (SVG,
который рисует сама страница: координатор в центре, кольца по числу хопов,
конечные устройства рядом с родителем, связи окрашены по LQI, таблица с
лучшим LQI каждого узла) и вкладка **Settings** (сведения о сети, смена
канала, мощность передатчика с применённым и запрошенным значением,
диапазоном чипа и подсказкой о нормах, сканирование каналов: загрузка в %
по каналам за 1–10 проходов с индикатором хода (проход k из N, прошло,
осталось) и кнопкой Stop, средняя или пиковая, отмечены канал Wi-Fi хаба
и любые каналы, которые укажет пользователь, рекомендация с объяснением и
сети Zigbee, услышанные на каждом канале, скачивание бэкапа, последний автоматический
бэкап, восстановление из файла пачками устройств, форма новой сети, требующая ввести
`RESET`, сведения о хабе, Wi-Fi, смена токена, перезагрузка, режим моста,
диагностика NCP и хвост журнала); элементы, которых нет у хаба или его NCP,
скрыты (`maintenance` в `hub/info`); пока идёт сканирование, страницей
можно пользоваться, а страница, открытая в это время, подхватывает его ход. Страница вместе с остальными вкладками
(включая Green Power) занимает 21,9 КБ после минификации и gzip (23,3 КБ без
минификации).

**Автоматизации (API 1.3).** Правила, которые выполняет сам хаб, без Home
Assistant и интернета (device-support 14.8): `automations/list`, `get`,
`validate`, `create`, `update`, `delete`, `enable`, `disable`, `run`
(тестовый запуск) и `traces` (последние 20 запусков: триггер, проверенные
условия, результат каждого действия, в том числе пришедший позже), события
в теме `automations`, `automations` в `hub/info`. Правило — триггеры →
условия → действия (пример: движение после 18:00 → свет включить, 90 с,
выключить; `mode` single или restart; `max_per_min`). Запуски
детерминированы и ограничены: 64 правила, по 16 действий, 16 запусков в
ожидании задержки, ограничение частоты на правило, а правило, которое
запустило бы само себя (напрямую или через другие правила, в пределах 10 с
после своей команды), останавливается как петля. Задержки идут по
монотонным часам; триггеры `time` (cron) и условия времени/дня недели ждут
синхронизации настенных часов (список это сообщает: `time_synced`,
`suspended`). Правила журналируются в `hubdata` и восстанавливаются при
старте; триггеры `start` срабатывают, когда поднята сессия с NCP. В
веб-интерфейсе есть вкладка **Automations** (правила с переключателем,
кнопками Run и Edit, форма простого правила — один триггер, необязательное
условие, команда или уведомление и необязательная вторая команда после
задержки, — JSON всего правила для остального, история запусков с трассой
каждого); интеграция Home Assistant показывает каждое правило
переключателем (включено) и кнопкой Run на устройстве хаба.
`hubctl --sim --sim-devices serve` добавляет две имитируемые розетки On/Off
и датчик температуры (симулятор устройств движка отвечает на опрос, чтения
и команды), чтобы попробовать их на компьютере;
`tools/hubctl/tests/automations_e2e.rs` проверяет через него цепочку
правил, петлю, задержку и жёсткий перезапуск. Цена на S3: образ приложения +62,5 КБ (2 568 464 → 2 630 992 Б: код +55,5 КБ, данные
только для чтения +7,0 КБ, из них веб-страница +2,7 КБ, теперь 25,5 КБ в
gzip), статическая ОЗУ не растёт; куча — около 1,2 КБ на правило и столько
же на трассу с ожидающим запуском (без правил — ничего); хаб, у которого
свободно меньше 48 КиБ кучи данных, новых правил не принимает.

**ОЗУ.** До hub 0.1.3 S3 на плате hwlab работал **без PSRAM** (в её модуле
N4R8 есть 8 МБ octal PSRAM, но сборки поддерживали только quad), поэтому
приложение жило в ~295 КБ внутренней кучи. При первом запуске на железе
(2026-11-20, разработческая таблица 4 МБ) память кончилась меньше чем за
секунду: компрессор deflate реестра (~250 КБ) и декодированный каталог
примеров (~90 КБ). Теперь реестр хранит обычный JSON (сжатые значения
прежних сборок читаются), каталог примеров грузится только при наличии
PSRAM, у потока приложения 40 КиБ стека, кольца UART в режиме хаба — 4/2
КиБ. В режиме хаба после импорта и опроса датчика C6: свободно ~106 КБ
внутренней кучи (минимум 103 КБ), Wi-Fi ещё не запущен. Поддержка PSRAM
включена (`CONFIG_SPIRAM`, при отсутствии игнорируется). Режим PSRAM
ESP-IDF задаёт при сборке, поэтому с 0.1.4 у каждой разметки два образа:
quad (`…-app.bin`: N4R2/N8R2, S3FH4R2 или без PSRAM) и octal
(`…-opi-app.bin`: N4R8/N8R8/N16R8, лабораторная плата); веб-прошивальщик
выбирает по встроенной PSRAM чипа, при ошибке плата просто работает без
PSRAM. В 0.1.3 плате *с* PSRAM не хватало внутренней памяти (N4R2: 4 КБ
свободно через минуту после загрузки, все служебные запросы отклонялись):
`malloc` держит запросы меньше `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL` во
внутренней памяти, а данные хаба — множество мелких выделений Rust, при
этом 2 МБ PSRAM оставались пустыми. С 0.1.4 выделения Rust идут в PSRAM
(`firmware/espapp/src/alloc.rs`; C-выделения больше 1 КиБ и буферы Wi-Fi/lwIP
тоже; стеки потоков остаются во внутренней памяти). Замер на ESP32-S3
SuperMini (S3FH4R2, 2 МБ quad) в режиме хаба без NCP, Wi-Fi включён: 0.1.3 —
8,4 КБ свободной внутренней памяти; 0.1.4 — 120 КБ (минимум 119 КБ при
установке всего каталога), занято 160 КБ PSRAM. На случай следующего сбоя `info` показывает стадию запуска
предыдущей загрузки, свободную кучу по стадиям, последний снимок стеков и
кучи, последнее сообщение паники Rust и причину сброса (RTC-память; логи
режима хаба идут в UART0, который хост лаборатории не видит); `hub stacks`
показывает текущую картину. В 0.1.9 главная задача завершается после старта
(её стек 8 КиБ возвращается в кучу), а lwIP собран без IPv6: +13 КБ
внутренней кучи. Замер на лабораторной плате (2026-11-23, Wi-Fi, два
устройства, одна сессия API): сборка octal — 117,8 → 131,0 КБ свободно
(минимум 113,0 → 125,9 КБ, наибольший блок 45 → 55 КБ); сборка quad на той же
плате, то есть без PSRAM, — 23,5 → 36,5 КБ свободно после загрузки (минимум
17,3 → 30,0 КБ). Без PSRAM поиск в каталоге (`definitions/list` с запросом)
в 0.1.8 приводил к неудачному выделению 10,5 КБ и перезапуску; 0.1.9 на него
отвечает (минимум 5 КБ свободно во время поиска, включая резервную копию и
сканирование энергии).

С Wi-Fi (2026-11-21): с настройками Wi-Fi по умолчанию оставалось 14–22 КБ
внутренней кучи, поэтому сборка хаба использует меньше буферов Wi-Fi
(4 статических RX, 8 динамических RX/TX, без A-MPDU) и держит код Wi-Fi,
FreeRTOS и кучи во флеше (`firmware/hub/sdkconfig.defaults`): с Wi-Fi,
HTTP-сервером и сессией WebSocket свободно **~65 КБ (минимум 57 КБ)**.
`ws://<ip>/api` с Mac: `devices/list` (C6), `entities/states` с живыми
температурой и влажностью, `network/permit_join` — всё отвечает. Найдено
по пути: первое подключение WebSocket вешало приложение — оно отправляло
кадр `auth_required` через detached sender esp_http_server (которому нужен
поток сервера), пока этот поток ждал в обработчике ответа приложения;
теперь `App::connect` вообще не ждёт поток приложения (номер сессии берётся
из общего счётчика), так как любая блокирующая отправка приложения
(события, пинги keepalive) может встретить поток сервера в обработчике;
сессии закрытых соединений снимаются по кадру Close, когда отправитель
сообщает о закрытом сокете, или когда не проходит пинг WebSocket раз в
30 с. Точка `/api` регистрируется прямыми вызовами esp_http_server
(`firmware/espapp/src/ws.rs`) с передачей управляющих кадров обработчику: с
`ws_handler` из esp-idf-svc (0.53) esp_http_server не дочитывает кадр PONG
от клиента, следующий кадр разбирается с его середины: esp-idf-svc паникует
на зарезервированном опкоде, либо соединение рвётся — клиент, отвечающий на
пинг хаба (браузер, интеграция HA), мог уронить хаб. Энергосбережение модема
Wi-Fi (по умолчанию в ESP-IDF) выключено: хаб питается от сети, а с ним кадры
к хабу ждали следующего маяка DTIM — пинг с Mac в среднем 91 мс (максимум
334 мс), `hub/info` туда-обратно: медиана 144 мс, p90 456 мс; с
`WIFI_PS_NONE` пинг в среднем 23 мс (максимум 90 мс), `hub/info`: медиана
68 мс, p90 134 мс. Кадры API ставятся в очередь потоку сервера без ожидания
(клиент, переставший читать, задерживал всех остальных на 1–2 с; теперь его
соединение закрывается, если он отстал на 32 кадра или отправка блокируется
дольше 2 с), сокеты WebSocket — с `TCP_NODELAY`, а ответы страницы закрывают
свой сокет (простаивающие keep-alive-сокеты браузера заставляли сервер на
пределе — теперь 7 сокетов — вытеснять давно не использованный сокет, то
есть WebSocket Home Assistant). После этого: ping/pong WebSocket — медиана
27 мс, `hub/info` — медиана 57 мс, p90 73 мс (собственный Wi-Fi Mac: ~17 мс
до точки доступа). PTA: образ NCP на H2 его не реализует (нет возможности
`PTA_COEX`), поэтому `coex_enable` не отправляется; Wi-Fi на канале 11,
Zigbee на 17 (не пересекаются). На macOS защита локальной сети может не
пускать неподписанный `hubctl` к адресам LAN («No route to host», хотя
`curl` работает): разрешите его в Системных настройках или пробросьте через
`nc` на localhost.

**Записанные размеры релиза 0.2.0.** Приложение рассчитано на разметку 8 МБ (слоты 3 МиБ; образы с
мостом MQTT, фича `mqtt`) и разработческую разметку 4 МБ (2 944 КиБ; без
него). `tools/build-hub-firmware.sh` собирает все четыре образа (quad и
octal PSRAM).

| Сборка (hub 0.2.0) | Образ приложения | Слот 3 МиБ | Слот разработки 2 944 КиБ |
|---|---:|---:|---:|
| Образ 8 МБ: `tbr-hub --features mqtt` (octal: +1 168 Б) | 2 858 192 Б | 91 % | — |
| Образ разработки 4 МБ: `tbr-hub` (приложение, по умолчанию; octal: +1 184 Б) | 2 618 688 Б | — | 87 % |
| `tbr-hub --no-default-features` (только ядро ZRHP-хоста) | 543 168 Б | 17 % | 18 % |

По сравнению с 0.1.10 (2 488 544 Б) образ 4 МБ вырос на 130 КБ: около
179 КБ на время, последние значения, консоль ZCL, автоматизации и группы,
минус 49 КБ «тихих» assert ESP-IDF; мост MQTT с esp-mqtt добавляет 240 КБ в
образах 8 МБ.

`tools/size-report.py` раскладывает ELF по владельцам. Сборка с приложением:
код Rust 1,49 МБ (`hub-devices` 432 КБ, `core` 232 КБ, `alloc` 151 КБ, `std`
148 КБ, `zdef` 113 КБ, `hub-app` 108 КБ, `hub-ncp` 93 КБ, serde и
`serde_json` 76 КБ, `ed25519-compact` 17 КБ), C 0,61 МБ (библиотеки Wi-Fi
175 КБ, mbedTLS 56 КБ, `wpa_supplicant` 54 КБ, lwIP 51 КБ, newlib 29 КБ,
httpd с парсером 22 КБ, TinyUSB 13 КБ) и 0,43 МБ констант и пулов литералов
без символа (в основном строки и таблицы Rust). Крупнейшие отдельные части —
тела потоков (101 КБ), разбор запросов API (serde, внутренне помеченный enum:
66 КБ), `ApiServer::dispatch` (53 КБ) и 11 копий стабильной сортировки std
(45 КБ, большей частью из `collect()` в `BTreeMap`/`BTreeSet`).

Сделано по размеру: fat LTO с opt-level `z` (обе прошивки; `s` на 81 КБ
больше), std без символизации бэктрейсов (−138 КБ, сообщения паники
остаются), более компактный `zdef` (zdef-size), а в 0.1.9 — семейство printf
из ROM (newlib «nano», −27 КБ; им пользуются только собственные строки
журнала ESP-IDF на UART0), lwIP без IPv6 (у хаба никогда не было IPv6-адреса;
−20 КБ) и минифицированная страница, вместе −55 КБ (было 2 568 416 Б); в
0.1.10 кодировщики `zdef` и отпечаток упорядочивают свои немногие ключи через
`zdef::small_sort` (стабильная сортировка вставками, тот же порядок) вместо
8 копий сортировки std (−25 КБ). Не
используются: `optimize_for_size` в std (−63 КБ кода сортировок, но его
стабильная сортировка встраивается в каждый вызывающий код с буфером 4 КиБ на
стеке: потоку приложения понадобилось на 13 КБ больше стека, и на железе два
старта завершились сбоем), `panic_immediate_abort` (~250 КБ, нет сообщений
паники) и `-Zlocation-detail=none` (−57 КБ, паника без файла и строки).
C-`assert` ESP-IDF «тихий» (`CONFIG_COMPILER_OPTIMIZATION_ASSERTIONS_SILENT`:
−49 КБ флеша, −5 КБ внутренней ОЗУ): сработавший вызывает abort на своём PC
без выражения и файла; бэктрейс на UART0 и core dump по-прежнему находят
место по ELF. Паники Rust сохраняют сообщения.

**Обход ошибки тулчейна.** Xtensa LLVM в Rust 1.90.0.0 падает при выборе
инструкций («Cannot select: i32 = Constant<5376>») на коде узлов btree
для карты слияния в `resolve` (листовые узлы по 5 376 Б); её значения
упакованы в `Box`.

**Тесты (хост).** `hub-app`: преобразование событий и режимов полезной
нагрузки GP-трансляций, сессия API с симулированным NCP (auth,
`devices/list`, подписка, присоединение доходит до движка, и его
Node_Desc_req уходит как `APS_DATA_REQUEST`), реестр переживает перезапуск
приложения (имя восстанавливается, удаление стирает запись), слоты ключей
каталога (слот 0 = закоммиченный PEM; чужой ключ отклоняется по kid).
`hub-devices`: снимок туда-обратно, измеренные значения не попадают,
восстановление самоописывающегося устройства без обмена. `hub-ncp`:
многочастные значения через уплотнение и оборванная запись.

## MQTT (совместимо с Zigbee2MQTT)

Хаб может публиковать свои устройства на MQTT-брокере **с топиками и
сообщениями Zigbee2MQTT**, поэтому с ним работают инструменты, сделанные
для Zigbee2MQTT: Node-RED (`node-red-contrib-zigbee2mqtt`), ioBroker,
openHAB, MQTT discovery Home Assistant, скрипты. `crates/hub-mqtt` —
клиент собственного WebSocket API хаба (сессия внутри процесса), поэтому
видит то же, что веб-интерфейс и интеграция HA.

- **Обычный MQTT 3.1.1 поверх TCP, без TLS** (хаб не делает TLS;
  транспорты SSL и WebSocket в esp-mqtt выключены при сборке): брокер в
  локальной сети (mosquitto, аддон HA …), по желанию с логином и паролем.
- **Настройки**: веб-интерфейс → Settings → MQTT или API
  (`mqtt/config/get`, `mqtt/config/set`, `mqtt/status`; device-support
  14.10); хранятся в NVS. Выключено, пока не включат. Хост и порт брокера,
  client ID (по умолчанию `zigbee-rs-hub-<6 hex IEEE координатора>`),
  логин/пароль, базовый топик (`zigbee2mqtt`), keepalive, discovery HA и
  его префикс (`homeassistant`), retain состояний/доступности, QoS.
- **Топики**: `<base>/<friendly_name>` (состояние JSON, ключи — имена
  exposes Zigbee2MQTT: `temperature`, `humidity`, `battery`, `voltage` (мВ),
  `state` `ON`/`OFF`, `brightness` 0–254, `color_temp` (майред), `color`,
  `action`, `linkquality` …), `…/set` и `…/get` (также `…/set/<свойство>`
  и формы с endpoint вроде `state_l1` или `<имя>/l1/set`),
  `…/availability` (`{"state":"online"}`), `bridge/state` (retained, LWT
  `offline`), `bridge/info`, `bridge/devices` (с `definition` и `exposes`),
  `bridge/event` (подключение, интервью, уход), `bridge/logging`,
  `bridge/request/permit_join`, `…/device/rename`, `…/device/remove`,
  `…/health_check` с `bridge/response/…` и transaction ID. Группы — позже.
- **Friendly name** — имя устройства в хабе (с суффиксом, если два
  совпадают); переименование где угодно (MQTT, веб-интерфейс, HA) очищает
  старые retained-топики, как в Zigbee2MQTT.
- **Home Assistant**: используйте **либо** интеграцию хаба
  (`integrations/home-assistant`), **либо** MQTT discovery (включается
  явно), не оба сразу — каждый создаёт те же устройства. Discovery как у
  Zigbee2MQTT (`unique_id` `<ieee>_<object>_<base>`, доступность через
  `bridge/state` и топик устройства).
- **Надёжность**: переподключение с нарастающей паузой (1–60 с), после
  переподключения или перезапуска HA (`homeassistant/status`) всё
  публикуется заново, исходящие сообщения формируются по мере отправки в
  очередь с ограничением в байтах (12 КБ без PSRAM), `bridge/devices` без
  exposes сверх 16 КБ на платах без PSRAM; на них мост запускается только
  при свободной внутренней куче не меньше 64 КБ (до тех пор состояние
  `low_memory` в `mqtt/status`).
- **Компьютер**: `hubctl --sim --sim-z2m-devices serve --mqtt HOST[:PORT]
  [--mqtt-discovery] [--mqtt-base T] [--mqtt-user U --mqtt-password P]
  [--mqtt-settings FILE]` запускает мост с четырьмя симулированными
  устройствами; `hubctl mqtt-broker` — маленький брокер для тестов (не для
  эксплуатации).
- **Прошивка**: MQTT входит в образы **4 МБ и 8 МБ** (cargo-фича `mqtt`,
  `tools/build-hub-firmware.sh`); манифест перечисляет фичи каждого образа.
  Без фичи API отвечает на `mqtt/*` ошибкой `unsupported`. В релизе 0.2.0
  MQTT был только на 8 МБ. `mqtt` — esp-mqtt из ESP-IDF; `mqtt-lite`
  (опция, не входит в стандартные образы) — собственный MQTT-клиент моста на
  сокетах lwIP (esp-mqtt тянет esp-tls и слой TLS mbedtls даже для
  обычного TCP; −62 КБ). Размер: +240 КБ (мост ~180 КБ, esp-mqtt с
  esp-tls/mbedtls ~62 КБ). Статическая
  RAM +1,5 КБ. Во время работы, только когда включено: поток моста (стек
  16 КБ), задача esp-mqtt (стек 5 КБ) с 2 КБ буферов и до 8 КБ outbox для
  QoS 1, очередь (≤ 12 КБ без PSRAM), модель устройств (3,4 КБ на
  устройство, измерено на 64-битном компьютере,
  `crates/hub-mqtt/tests/heap.rs`; на S3 меньше) и ненадолго снимок API,
  который мост разбирает по одной записи.

## Обновление прошивок устройств (Zigbee OTA)

Черновик (ветка `zigbee-ota-v2`, [docs/ota.md](docs/ota.md), API — раздел
14.11 device-support): хаб — OTA-сервер (кластер 0x0019) своей сети и сам
ничего не скачивает. Два источника образов: **потоковая отдача**:
подключённый клиент — Home Assistant (предпочтительно), вкладка браузера
(**Updates** в сборке без хранилища, «не закрывайте вкладку»), `hubctl
ota-stream` — предлагает файл, который держит у себя, и отвечает на
`ota/block_needed` сообщением `ota/block_data`; хаб держит окно 4 КиБ на
поток (не больше 4 потоков с PSRAM, `Resources::ota_streams`), пока кусок
в пути, отвечает устройству WAIT_FOR_DATA и аккуратно завершает передачу,
если клиент пропал (устройство повторит позже). **Хранилище образов**
(только образы 8 МБ, фича `ota-store`): загрузки (веб-интерфейс, Home
Assistant, `hubctl ota-upload`; с докачкой, `replace` в begin, проверка по
флешу: заголовок, подэлементы, SHA-256) пишутся в **неактивный слот
приложения** (3 МиБ) — взаимоисключение с самообновлением хаба в обе
стороны, образы теряются при обновлении хаба, при загрузке
перепроверяются. **Zigbee OTA есть только в образах 8 МБ** (фича `ota`,
её включает `ota-store`): образы 4 МБ собираются без него (`ota/*`
отвечает `unsupported`, эндпоинт хаба не объявляет 0x0019 — сохранённый
старым образом эндпоинт регистрируется заново при старте, — а Query Next
Image устройства получает только запрошенный Default Response, как до
сервера). Индекс Koenkk/zigbee-OTA
скачивает Home Assistant (у веб-страницы поиска по индексу нет; бюджет
страницы 36 КиБ gzip). Для каждого устройства: политика `manual`
(по умолчанию), `auto` (окно расписания) или `off` (никогда: `ota/start`
отклоняется, идущая задача прерывается; решено);
Image Notify (спящим — через очередь); блоки min(устройство, 48 Б,
`max_asdu` NCP − 17); запросы страниц — по одному блоку за раз (не больше
128, решено; в общей очереди темпа с другими устройствами); темп; не больше 2
загрузок одновременно; отмена (прерванный или не одобренный Upgrade End
получает ABORT, а не «ставь сейчас»); события прогресса; продолжение
после перезапуска хаба. Home Assistant: сущность `update` на устройство
(загрузка в хранилище или поток). Тесты на хосте: симулированный
OTA-клиент за симулированным NCP, Home Assistant сквозняком с `hubctl
--sim --sim-ota`. Железо (octal-плата 4 МБ,
лабораторная сборка этой ветки 6efb7ab с `ota`): C6 на zigbee-rs
обновлён потоком дважды, с уходом клиента и перезапуском хаба посреди
загрузки, без паник, внутренняя куча ровная (результаты в
[docs/ota.md](docs/ota.md#hardware-results)); ещё не на железе:
хранилище на 8 МБ. Образ приложения
относительно main (3c777d2, quad PSRAM, CI): 8 МБ
(`mqtt,advanced,ota-store`) 2 933 504 Б, +131 232 Б, 93,3 % слота 3 МиБ;
4 МБ (`mqtt`, без Zigbee OTA) 2 785 520 Б, +3 632 Б (общая обвязка во
всех образах: кластеры приложения и их исходы, события сериализуются
один раз), 92,4 % слота 2 944 КиБ;
статическая RAM не растёт. Открыто: самообновление хаба должно брать
блокировку слота. Устройства zigbee-rs объявляют код производителя OTA
0x6D6B (устройствам на старой прошивке — один переходный файл с 0x1234).

## Интеграция с Home Assistant

`integrations/home-assistant/custom_components/zigbee_rs_hub` — пользовательская
интеграция для Home Assistant: одно постоянное WebSocket-соединение с
`ws://<хаб>/api` (токен — команда консоли хаба `token`), устройство HA на
каждое Zigbee/GP-устройство, сущности из модели сущностей хаба (раздел 4
device-support) с живым состоянием, которое присылает хаб, команды через
`entities/command`, разрешение подключения (кнопка и сервис), удаление
устройств, диагностика. Хаб опознаётся по `hub/info` (`coordinator_ieee`,
добавлен для неё; минорное расширение API). Zigbee-группы хаба видны как
устройства со световой сущностью или выключателем группы, их сцены — как
сцены HA (device-support 14.9); удаление устройства группы в HA удаляет
группу. Установка, тесты и соответствие API:
[integrations/home-assistant/README.md](integrations/home-assistant/README.md)
(на английском).

Интеграция также клиент каталога: хаб сам ничего не скачивает, поэтому Home
Assistant берёт подписанные файлы релиза с зеркала, заданного на хабе
(`catalog/config` `base_url`, по умолчанию GitHub Pages), и загружает их
через API частями по 4 КиБ с продолжением после обрыва соединения. Сервис
`zigbee_rs_hub.update_catalog` (необязательные `config_entry_id`, `force`,
`base_url`) запускает это по требованию; иначе — раз в 24 ч (первый раз через
две минуты после настройки), насколько разрешают `auto_update` / `auto_fetch`
хаба, и по событиям `definition_needed`, если включён `auto_fetch`. Сенсор
**Версия каталога** показывает установленный банк.
